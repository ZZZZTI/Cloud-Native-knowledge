> SRE 写并发脚本的目的只有一个：把「逐个串行」变成「批量并行」，典型是同时探测几百个节点或调几百次 API。
>
> GIL，线程池，进程池，asyncio，超时与取消，限流

------

### 先选模型，再写代码

| 场景 | 用什么 | 原因 |
| :-- | :-- | :-- |
| 批量 HTTP 请求、批量 SSH、批量查库 | **线程池** 或 **asyncio** | IO 密集，等待时间占绝大部分 |
| 大量日志正则匹配、压缩、计算哈希 | **进程池** | CPU 密集，多线程受 GIL 限制 |
| 要同时管上千个连接 | **asyncio** | 单线程事件循环，内存开销远小于线程 |
| 只有十几二十个任务 | 线程池就够了 | 不必上 asyncio，复杂度不值得 |

**GIL（全局解释器锁）**：同一时刻只有一个线程执行 Python 字节码。所以多线程**不能**加速纯计算，但**能**加速 IO 等待——因为等待时会释放 GIL。

### 线程池：IO 密集的首选

```python
from concurrent.futures import ThreadPoolExecutor, as_completed
import requests

HOSTS = [f"10.0.0.{i}" for i in range(1, 101)]

def probe(host: str) -> tuple[str, bool, float]:
    try:
        r = requests.get(f"http://{host}:9100/metrics", timeout=3)
        return host, r.ok, r.elapsed.total_seconds()
    except requests.RequestException:
        return host, False, 0.0

results = []
with ThreadPoolExecutor(max_workers=20) as pool:
    futures = {pool.submit(probe, h): h for h in HOSTS}
    for fut in as_completed(futures):        # 谁先完成先处理
        host, ok, cost = fut.result()
        results.append((host, ok, cost))
        if not ok:
            print("不可达:", host)

print(f"{sum(ok for _, ok, _ in results)}/{len(results)} 正常")
```

**并发数不是越大越好**：IO 密集一般 10–50 就够；太高会把对端打挂、或本地文件描述符耗尽。

### 进程池：CPU 密集

```python
from concurrent.futures import ProcessPoolExecutor
from pathlib import Path
import hashlib

def sha256(path: str) -> tuple[str, str]:
    h = hashlib.sha256()
    with open(path, "rb") as f:
        for chunk in iter(lambda: f.read(1 << 20), b""):
            h.update(chunk)
    return path, h.hexdigest()

files = [str(p) for p in Path("/data").rglob("*.tar")]
with ProcessPoolExecutor() as pool:
    for path, digest in pool.map(sha256, files):
        print(digest[:12], path)
```

注意：进程池的参数和返回值**必须可 pickle**，传不了连接对象、文件句柄、lambda。

### asyncio：高并发的最优选

```python
import asyncio, httpx

async def probe(client: "httpx.AsyncClient", host: str) -> tuple[str, bool]:
    try:
        r = await client.get(f"http://{host}:9100/metrics", timeout=3)
        return host, r.is_success
    except Exception:
        return host, False

async def main(hosts: list[str]) -> None:
    sem = asyncio.Semaphore(50)              # 限流：同时最多 50 个

    async def one(host: str):
        async with sem:                      # 拿到令牌才发请求
            return await probe(client, host)

    async with httpx.AsyncClient() as c:
        client = c
        results = await asyncio.gather(*(one(h) for h in hosts))
    print(sum(ok for _, ok in results), "/", len(results))

asyncio.run(main([f"10.0.0.{i}" for i in range(1, 501)]))
```

```python
# 超时：3.11+ 用 asyncio.timeout，之前的版本用 wait_for
async with asyncio.timeout(10):
    await do_something()

# 不要用 gather 一把梭，需要容错时用 return_exceptions
results = await asyncio.gather(*tasks, return_exceptions=True)
for r in results:
    if isinstance(r, Exception):
        print("失败:", r)
```

### 超时与取消

**没有超时的并发脚本 = 半夜卡死事故。** 三层都要设：

```python
requests.get(url, timeout=(3.05, 10))   # (连接超时, 读取超时)
subprocess.run(cmd, timeout=30)         # 外部命令
asyncio.timeout(10)                     # 协程
```

线程池无法真正「杀掉」正在跑的线程，只能让任务自己检查超时；所以**超时要下沉到具体的 IO 调用里**，靠外层强杀是不可靠的。

### 常见坑

```python
# ❌ 线程间共享可变状态却不加锁
counter += 1                    # 读到写之间可能被切换

# ✅ 用锁
lock = threading.Lock()
with lock:
    counter += 1

# ✅ 更好的做法：让每个任务返回结果，最后统一汇总（无共享状态）
```

```python
# ❌ 在 asyncio 里调用同步阻塞库（requests、time.sleep）
time.sleep(1)                   # 会卡住整个事件循环

# ✅ 用异步版本或丢进线程池
await asyncio.sleep(1)
await asyncio.to_thread(requests.get, url)
```

```python
# ❌ 忘了给 futures 设上限，10 万个任务一次提交
pool.submit(...) for i in range(100000)

# ✅ 分批提交，或用 asyncio.Semaphore 限流
```

### 核心概念

1. **先分清 IO 密集还是 CPU 密集**，再决定线程 / 进程 / 协程，选错就是白写。
2. **GIL 让多线程不能加速计算**，但 IO 等待时会释放，所以批量请求用线程池完全够用。
3. **并发度要有上限**（`max_workers` 或 `Semaphore`），无限并发等于自己打自己。
4. **每一层都要有超时**：连接超时、读取超时、命令超时、协程超时。
5. **优先「无共享状态」**：任务各自返回结果，主线程汇总，比加锁干净。
6. **asyncio 里禁止调用同步阻塞代码**，用 `asyncio.to_thread` 或换异步库。
7. **进程池的入参出参必须可 pickle**，别传连接对象。
