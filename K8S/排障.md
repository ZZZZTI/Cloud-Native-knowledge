```Shell
1. 看现象：是 Pod 问题？Service 问题？Ingress 问题？节点问题？应用问题？
2. kubectl get：确认资源状态（Running/Pending/CrashLoopBackOff）
3. kubectl describe：看 Events，找关键错误信息
4. kubectl logs / --previous：看应用日志
5. kubectl exec：进容器验证配置、网络、文件
6. 查 Service/Endpoints：Endpoints 是否为空？selector 是否匹配？
7. 查 DNS：nslookup / dig 测试域名解析
8. 查 NetworkPolicy：是否被隔离？
9. 查存储：PVC 是否 Bound？PV 是否可用？
10. 查节点/控制面：kubelet、apiserver、etcd 是否正常？

kubectl get pods -A -o wide                 # 全局视角
kubectl get pod <pod> -o yaml               # 查看完整状态（status.conditions）
kubectl describe pod <pod>                  # 【最重要】看 Events
kubectl get events -A --sort-by=.metadata.creationTimestamp
kubectl get endpoints <svc>                 # 检查 Service 后端
kubectl get endpointslices                  # 新版端点切片
kubectl get pv,pvc,sc                       # 存储链路
kubectl get nodes -o wide                   # 节点状态

kubectl logs <pod>                          # 当前日志
kubectl logs <pod> --previous               # 上次崩溃日志（CrashLoopBackOff 必看）
kubectl logs -f <pod> --tail=100            # 实时跟踪
kubectl logs <pod> -c <container>           # 多容器指定容器
kubectl exec -it <pod> -- sh                # 进入容器
kubectl cp <pod>:/path ./local              # 拷贝文件
kubectl port-forward svc/<svc> 8080:80      # 本地访问
kubectl debug <pod> -it --image=busybox     # 临时调试容器（不改变原 Pod）

kubectl auth can-i --list                   # 检查权限

码  含义	              典型场景
0	  正常退出	         Job 完成；前台进程退出也会 0 → CrashLoopBackOff
1	  应用报错退出	      配置错误、依赖连不上、参数不合法
126	命令不可执行	      入口脚本没有可执行权限
127	命令找不到	command  写了镜像里没有的二进制
137	128+9(SIGKILL)	  OOMKilled 或 kubectl delete 强杀
143	128+15(SIGTERM)	  优雅终止超时后被杀
139	SIGSEGV	          程序段错误（架构不匹配最常见）
```



### 核心概念

1. **三件套**：`get`（现状）→ `describe`（Events/配置）→ `logs`（应用）。
2. **事件**：`kubectl get events --sort-by=.lastTimestamp`；默认只保留 1 小时。
3. **指标**：metrics-server 提供 `kubectl top`（HPA 也依赖它）。生产用 Prometheus + Grafana。
4. **日志**：容器日志在节点上（`/var/log/pods`）；`kubectl logs -f`、`--previous`、`--all-containers`、`--since`。
   - 日志架构三选一：节点 Agent（DaemonSet）/ Sidecar / 直接推远端。
5. **调试利器**
   - `kubectl debug`（临时容器）—— 镜像里没有 shell 也能救
   - `kubectl debug node/<node>` —— 起一个特权 Pod 挂宿主机根目录
   - `kubectl port-forward` / `kubectl cp` / `kubectl exec`
   - **k9s**：图形化看事件、日志、资源，效率倍增（`k9s` 直接敲）
6. **节点级排障**：`crictl ps/logs`、`journalctl -u kubelet`、`systemctl status containerd`（在 kind 节点容器里执行）。

### 排障决策树（背下来）

| 现象                         | 第一步                               | 常见原因                                                     |
| ---------------------------- | ------------------------------------ | ------------------------------------------------------------ |
| `ImagePullBackOff`           | `describe pod` 看 Events             | 镜像名/标签错、私有仓库缺 imagePullSecret、**网络不通/加速失效** |
| `CrashLoopBackOff`           | `logs --previous`                    | 应用配置错、依赖服务连不上、探针太激进、命令写错             |
| `Pending`                    | `describe pod` 看 Events             | 资源不足、亲和性/污点不满足、PVC Pending、超配额             |
| `OOMKilled`                  | `describe pod` 看 Last State         | `limits` 太小、内存泄漏、JVM 堆未设上限                      |
| `Running` 但 Service 不通    | `get endpoints`                      | selector 不匹配、Pod 未 Ready、targetPort 错                 |
| `CreateContainerConfigError` | `describe pod`                       | 引用的 ConfigMap/Secret 不存在或 key 缺失                    |
| `Evicted`                    | `describe node` / `get events`       | 节点磁盘/内存压力，`kubelet` 驱逐                            |
| 无法访问 Ingress             | `describe ingress` + Controller 日志 | 没装 Controller、ingressClassName 错、后端 Service 名错      |
