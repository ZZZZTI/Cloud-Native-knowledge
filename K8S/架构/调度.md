> 调度：Filter（nodeSelector，nodeAffinity），Score，Taint/Toleration，配额与限制
>

------

### 概念

```Shell
# 调度流程
过滤（Filter）：排除不满足条件的节点 → 打分（Score）：选最高分 → 绑定（Bind），失败则Pod停在Pending


# 影响调度的因素（Pod 主动选择节点）
resources.requests（节点剩余可分配资源）
nodeSelector（标签匹配）
nodeAffinity：硬约束（过滤阶段）+ 软约束（打分阶段）
podAffinity/podAntiAffinity：让新 Pod 倾向/避免与某些现有 Pod 运行在同一个拓扑域
topologySpreadConstraints：精确控制每个拓扑域的数量差异


# 节点主动拒绝 Pod 的策略
容忍（Toleration）：Pod 的“通行证”，允许其被调度到带有对应污点的节点上。
污点（Taint）：打在node上的“标签”，表明该节点具有某种特殊属性（如专用 GPU、故障状态），默认排斥所有 Pod。
污点类型	           行为
NoSchedule	     	  不容忍的新 Pod 不调度；已运行的不动	
PreferNoSchedule		软排斥，尽量不调度，不保证	         
NoExecute	        	不容忍的已运行，Pod 被驱逐；新 Pod 也不调度


# 调度控制器
HPA (HorizontalPodAutoscaler)（自动扩缩）
根据 CPU/内存或自定义指标，自动弹性调整 Deployment/StatefulSet 的副本数。
强依赖 metrics-server，生产环境必须配置 behavior 缩容冷却时间防抖。
# 期望副本数 = ceil（向上取整）[ 当前副本数 × ( 当前指标值 / 目标指标值 ) ]

PDB (PodDisruptionBudget)（节点维护）
保障应用在主动驱逐（排空节点、集群缩容、升级节点内核）时，至少有指定数量的 Pod 保持可用。
只能拦截“自愿中断”操作，无法阻止节点宕机、OOM 等“非自愿中断”。


# Qos class（服务质量）：是 K8s 用来决定 Pod 在节点资源紧张时优先级的一种机制。
1.Guaranteed（保证型）：资源分配最稳定，最不容易被驱逐。
条件：Pod 中每一个容器的 requests 必须严格等于 limits
2.Burstable（突发型）：允许容器在空闲时突发使用超出 requests 的资源，但不能超过 limits
条件：Pod 中至少有一个容器设置了 requests 或 limits。
3.BestEffort（尽力而为型）：一旦节点资源紧张，这类 Pod 会被最先杀掉。
条件：Pod 中所有容器都没有设置任何 requests 和 limits。


CPU  可压缩资源   超 limits.cpu 被 throttle（CFS 节流），表现为"变慢"，不会被杀
内存 不可压缩资源  超 limits.memory 被 OOMKilled，退出码 137
```

### 节点维护与调度控制

```Shell
kubectl cordon <node>                        # 将节点标记为不可调度（不驱逐现有Pod，新Pod不会被调度）
kubectl uncordon <node>                      # 解除不可调度标记
kubectl drain <node> --ignore-daemonsets --delete-emptydir-data  # 驱逐节点上的 Pod（维护前使用）
kubectl taint node <node> key=value:NoSchedule   # 给节点添加污点
kubectl taint node <node> key=value:NoSchedule-  # 移除污点（末尾加 -）
kubectl label node <node> disktype=ssd       # 给节点打标签
```

### Pod.yaml / Deployment.yaml中的调度相关字段

```Shell
apiVersion: v1
kind: Pod
metadata:
  name: scheduling-demo
spec:
  # ============================================================
  # 1. 节点选择器 (NodeSelector) - 最基础的硬匹配
  # ============================================================
  nodeSelector:
    disktype: ssd            # Pod 只会被调度到带有 disktype=ssd 标签的节点

  # ============================================================
  # 2. 节点亲和性 (Node Affinity) - 高级硬/软匹配
  # ============================================================
  affinity:
    nodeAffinity:
      # 【硬限制】必须满足，否则 Pod 保持 Pending
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
          - matchExpressions:
              - key: topology.kubernetes.io/zone
                operator: In               # 支持 In, NotIn, Exists, DoesNotExist, Gt, Lt
                values: ["zone-a", "zone-b"]
      # 【软限制】优先满足，不满足也能调度，只是得分低
      preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 80                       # 权重 1-100
          preference:
            matchExpressions:
              - key: node-type
                operator: In
                values: ["gpu"]

    # ============================================================
    # 3. Pod亲和与反亲和 (Pod Affinity / Anti-Affinity)
    # ============================================================
    podAntiAffinity:
      # 【硬限制】强制要求：同一应用的 Pod 绝对不能调度到同一个节点
      requiredDuringSchedulingIgnoredDuringExecution:
        - labelSelector:
            matchLabels:
              app: my-app
          topologyKey: kubernetes.io/hostname  # 以节点名为拓扑域（即跨节点）

  # ============================================================
  # 4. 拓扑分布约束 (Topology Spread Constraints) - K8s 1.19+ 推荐
  # 将 Pod 尽可能均匀地分布在不同的可用区或节点
  # ============================================================
  topologySpreadConstraints:
    - maxSkew: 1                       # 允许的最大倾斜度（最多相差 1 个）
      topologyKey: topology.kubernetes.io/zone
      whenUnsatisfiable: DoNotSchedule # DoNotSchedule(硬) 或 ScheduleAnyway(软)
      labelSelector:
        matchLabels:
          app: my-app

  # ============================================================
  # 5. 容忍度 (Tolerations) - 配合节点的 Taint 使用
  # ============================================================
  tolerations:
    # 精确匹配特定的污点
    - key: "dedicated"
      operator: "Equal"                # Equal 或 Exists
      value: "gpu"
      effect: "NoSchedule"             # NoSchedule, PreferNoSchedule, NoExecute
    # 容忍所有 NotReady 状态（常用于 DaemonSet）
    - key: "node.kubernetes.io/not-ready"
      operator: "Exists"
      effect: "NoExecute"
      tolerationSeconds: 300           # 节点 NotReady 后还能在上面存活 300 秒

  # ============================================================
  # 6. 优先级与抢占 (PriorityClass)
  # ============================================================
  priorityClassName: high-priority     # 资源不足时，此 Pod 会驱逐低优先级的 Pod
```

### HPA 

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: my-app-hpa
  namespace: default
spec:
  # 1. 扩缩容目标（必须与目标 Deployment 在同一个 namespace）
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: my-app-deployment

  # 2. 副本数范围
  minReplicas: 2                   # 最小副本数（即使没流量也保留 2 个保证高可用）
  maxReplicas: 10                  # 最大副本数（防止扩缩容导致资源耗尽）

  # 3. 指标配置（可以配多个，HPA 会取计算结果的【最大值】进行扩容）
  metrics:
    # 指标一：基于 CPU 利用率
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70   # 目标：平均 CPU 使用率达到 requests 的 70%

    # 指标二：基于内存利用率（注意：内存通常只扩不缩，因为有 GC 延迟）
    - type: Resource
      resource:
        name: memory
        target:
          type: Utilization
          averageUtilization: 80   # 目标：平均内存使用率达到 requests 的 80%

    # 指标三（示例）：基于自定义业务指标（如 Prometheus 采集的 QPS，需要配合适配器）
    # - type: Pods
    #   pods:
    #     metric:
    #       name: http_requests_per_second
    #     target:
    #       type: AverageValue
    #       averageValue: 1k        # 目标：每个 Pod 每秒处理 1000 个请求

  # 4. 扩缩容行为控制（极其重要，防止指标抖动导致频繁扩缩容）
  behavior:
    # 扩容行为
    scaleUp:
      stabilizationWindowSeconds: 0      # 扩容无需等待，检测到超标立刻扩（默认 0）
      policies:
        - type: Percent
          value: 100                     # 每次扩容最多翻倍（例如从 2 扩到 4，下次从 4 扩到 8）
          periodSeconds: 15              # 每 15 秒允许触发一次扩容
        - type: Pods
          value: 4                       # 或者每次最多加 4 个 Pod
          periodSeconds: 15
      selectPolicy: Max                  # 选择上面策略中允许扩容数量最大的那个
      
    # 缩容行为
    scaleDown:
      stabilizationWindowSeconds: 300    # 【神级防抖】过去 5 分钟内的推荐副本数，取最大值（防止流量闪降立刻缩容）
      policies:
        - type: Percent
          value: 10                      # 每次缩容最多减少当前副本数的 10%
          periodSeconds: 60              # 每 60 秒允许缩容一次（慢慢缩，给应用缓冲时间）
```

### PDB

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: my-app-pdb
  namespace: default
spec:
  # 1. 选择要保护的目标 Pod（通常与 Deployment 的标签匹配）
  selector:
    matchLabels:
      app: my-app

  # 2. 中断底线（二选一）
  # 方式 A：保证至少有 2 个 Pod 存活（可以是数字，也可以是百分比 "50%"）
  minAvailable: 2
  
  # 方式 B：最多允许 1 个 Pod 同时不可用
  # maxUnavailable: 1
```

### ResourceQuota.yaml 和 LimitRange.yaml

```Shell
# ===============================================================================
# 设置整个命名空间的资源总和
# ===============================================================================
apiVersion: v1
kind: ResourceQuota          
metadata:
  name: tenant-quota
  namespace: tenant-a        # 作用于哪个命名空间
spec:
  hard:
    # ============================================================
    # 1. 计算资源限制（最常用）
    # ============================================================
    requests.cpu: "10"       # 该命名空间所有 Pod 的 CPU 请求总和不能超过 10 核
    requests.memory: 20Gi    # 内存请求总和不能超过 20Gi
    limits.cpu: "20"         # CPU 上限总和不能超过 20 核
    limits.memory: 40Gi      # 内存上限总和不能超过 40Gi

    # ============================================================
    # 2. 存储资源限制
    # ============================================================
    requests.storage: 100Gi  # 该命名空间下所有 PVC 申请容量总和不能超过 100Gi
    persistentvolumeclaims: "10" # 最多只能创建 10 个 PVC
    # standard.storageclass.storage.k8s.io/requests.storage: 50Gi # 针对特定 SC 的限制

    # ============================================================
    # 3. 对象数量限制（防滥用）
    # ============================================================
    pods: "50"               # 最多创建 50 个 Pod
    services: "20"           # 最多创建 20 个 Service

    configmaps: "20"         # 最多 20 个 ConfigMap
    secrets: "20"            # 最多 20 个 Secret
    count/deployments.apps: "10" # 最多 10 个 Deployment（注意 API 组后缀）
```

### PriorityClass.yaml（优先级与抢占）

```Shell
# ============================================================
# 1. 定义高优先级（用于核心网关、支付等绝对不能挂的业务）
# ============================================================
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: high-priority
value: 1000000                 # 【核心】整数，越大优先级越高
globalDefault: false           # 是否设为全局默认（整个集群只能有一个 true）
description: "Used for core business."
preemptionPolicy: PreemptLowerPriority  # 默认策略：允许抢占低优先级的 Pod

---
# ============================================================
# 2. 定义低优先级（用于离线计算、日志收集、边缘业务）
# ============================================================
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: low-priority
value: -10                     # 允许设置负数
globalDefault: false
description: "Used for batch jobs."
preemptionPolicy: Never        # 设为 Never 后，即使资源不足也不去抢占别人的资源，乖乖 Pending
```
