### 核心概念

1. **Pod IP 是易变的** → 需要 Service 提供稳定虚拟 IP（VIP）。
2. **Service 四种类型**
   - `ClusterIP`（默认）：集群内 VIP
   - `NodePort`：在每个节点上开一个端口（默认 30000-32767）
   - `LoadBalancer`：需云厂商/`MetalLB` 支持
   - `ExternalName`：CNAME 到外部域名
3. **Endpoints / EndpointSlice**：Service 的 `selector` 匹配到的 Pod IP 列表 = 真实后端。
   - **没有 Endpoints = Service 不可用**，这是最常见的排查点（selector 不匹配 / Pod 没 Ready）。
4. **kube-proxy**：把 Service VIP:Port 翻译成 iptables/IPVS 规则实现转发（不是进程代理）。
5. **Headless Service**（`clusterIP: None`）：不做 VIP，直接返回所有 Pod IP，供 StatefulSet 用。
6. **DNS**：CoreDNS 提供
   - Service：`<svc>.<ns>.svc.cluster.local`
   - Pod：`<pod-ip-dashed>.<ns>.pod.cluster.local`
   - SRV 记录用于发现端口；`/etc/resolv.conf` 里的 `search` 与 `ndots:5` 决定了解析顺序
7. **Ingress**：L7 HTTP 路由（需要 Ingress Controller 才生效，kind 默认没有）
   - `ingressClassName`、`pathType: Prefix/Exact`、`tls`、注解（rewrite、超时、限流）
8. **NetworkPolicy**：Pod 级防火墙，**默认全通**，加了策略才隔离。
   - ✅ **本集群实测：kindnet 会真实执行策略**（kind 0.33 + k8s 1.37）：无策略时连通，加 deny-all 后不通，再加白名单标签后有标签通、无标签不通。网上"kind 默认 CNI 不支持 NetworkPolicy"的说法已经过时；但结论取决于 CNI 实现与版本，**务必亲手实验确认**（通=没强制，不通=真强制）。
9. **CNI 插件**：负责给 Pod 分配 IP、打通跨节点网络。







```Shell
# ============================================================
# Service 服务
# 作用：为一组 Pod 提供稳定的访问入口和负载均衡
# ============================================================
apiVersion: v1
kind: Service
metadata:
  name: web-service
  namespace: demo-namespace
  labels:
    app: web
spec:
  type: ClusterIP          # ClusterIP（默认，集群内）, NodePort, LoadBalancer, ExternalName
  selector:
    app: web               # 选择带有 app=web 标签的 Pod 作为后端
  ports:
    - name: http
      port: 80             # Service 暴露的端口
      targetPort: 80       # 容器监听的端口（对应 containerPort）
      protocol: TCP
      # nodePort: 30080    # 当 type=NodePort 时，可指定节点端口（30000-32767）
  sessionAffinity: None    # 会话保持策略，None 或 ClientIP

---

# ============================================================
# Ingress 七层路由
# 作用：提供 HTTP/HTTPS 外部访问入口，需要 Ingress Controller
# ============================================================
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-ingress
  namespace: demo-namespace
  annotations:
    # 常用 Nginx Ingress Controller 注解
    nginx.ingress.kubernetes.io/rewrite-target: /
    nginx.ingress.kubernetes.io/ssl-redirect: "false"
spec:
  ingressClassName: nginx  # 指定 Ingress Controller 类型（如 nginx, traefik）
  rules:
    - host: demo.example.com  # 域名，如果为空则匹配所有
      http:
        paths:
          - path: /
            pathType: Prefix  # Prefix（前缀匹配）, Exact（精确匹配）
            backend:
              service:
                name: web-service
                port:
                  number: 80
  # TLS 配置（需要 Secret 中存放证书）
  # tls:
  #   - hosts:
  #       - demo.example.com
  #     secretName: tls-secret
```





## 网络

### Pod 网络模型

三条铁律：

1. 每个 Pod 有独立 IP，所有 Pod 之间可直连（无 NAT）。
2. 所有节点与 Pod 之间可直连（无 NAT）。
3. Pod 看到的自己的 IP 和别人看到的一样。

由 **CNI 插件**负责实现，跨节点 Pod 通信方案分 Overlay（VXLAN/IPIP，如 Flannel）和 Underlay/BGP（如 Calico BGP 模式）。

### Service

```yaml
apiVersion: v1
kind: Service
metadata: { name: web }
spec:
  type: ClusterIP              # ClusterIP / NodePort / LoadBalancer / ExternalName
  selector: { app: web }       # 靠这个选 Pod，写错就 0 端点
  ports:
    - name: http
      port: 80                 # Service 端口
      targetPort: http         # 容器端口（名字或数字）
      protocol: TCP
      nodePort: 30080          # NodePort 类型可指定，范围 30000-32767
  sessionAffinity: None        # 或 ClientIP
  externalTrafficPolicy: Local # LoadBalancer/NodePort：Local 保留源 IP
```

| 类型                          | 访问范围                 | 说明                                         |
| :---------------------------- | :----------------------- | :------------------------------------------- |
| `ClusterIP`                   | 集群内                   | 默认，虚拟 IP                                |
| `NodePort`                    | 集群外（节点 IP + 端口） | 在 ClusterIP 基础上每节点开一个端口          |
| `LoadBalancer`                | 集群外（云 LB）          | 依赖 cloud-controller-manager 或 MetalLB     |
| `ExternalName`                | —                        | 只做 DNS CNAME，无代理                       |
| Headless（`clusterIP: None`） | 集群内                   | DNS 直接返回 Pod IP 列表，StatefulSet 依赖它 |

**kube-proxy 模式**：

| 模式       | 特点                                             |
| :--------- | :----------------------------------------------- |
| `iptables` | 默认，规则多时线性增长、性能下降                 |
| `ipvs`     | 哈希表查找，大规模集群性能更好，支持多种调度算法 |
| `nftables` | 较新（1.31+ beta），替代 iptables                |

### EndpointSlice

Service 的 `selector` 匹配到的 Pod IP 集合会被记录为 EndpointSlice（旧版是 Endpoints 对象，现已弃用）。

```bash
kubectl get endpointslices -l kubernetes.io/service-name=web
```

**Service 不通的第一件事**：看 Endpoints 是不是空的——空说明 `selector` 没匹配上 Pod，或 Pod 没 Ready（readinessProbe 失败也会摘除）。

### Ingress

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
    nginx.ingress.kubernetes.io/proxy-body-size: "50m"
spec:
  ingressClassName: nginx
  tls:
    - hosts: [app.example.com]
      secretName: web-tls
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /
            pathType: Prefix        # Prefix / Exact / ImplementationSpecific
            backend:
              service:
                name: web
                port: { number: 80 }
```

Ingress 只是**路由规则**，必须有一个 Ingress Controller（ingress-nginx / Traefik / HAProxy）在跑才会生效——这是新手最常见的误区。Gateway API 是 Ingress 的下一代替代，表达力更强。

### NetworkPolicy

Pod 防火墙，**默认全通**，一旦某 Pod 被任何 NetworkPolicy 选中，就变成「只有明确允许的才通」。

```yaml
# 1) 命名空间默认拒绝所有入站和出站
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: default-deny-all }
spec:
  podSelector: {}                # 空 = 选中本命名空间所有 Pod
  policyTypes: [Ingress, Egress]
---
# 2) 只放行指定流量
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: web-allow }
spec:
  podSelector:
    matchLabels: { app: web }
  policyTypes: [Ingress, Egress]
  ingress:
    - from:
        - namespaceSelector:
            matchLabels: { kubernetes.io/metadata.name: ingress-nginx }
        - podSelector:
            matchLabels: { app: frontend }
      ports:
        - { protocol: TCP, port: 8080 }
  egress:
    - to:
        - podSelector:
            matchLabels: { app: db }
      ports:
        - { protocol: TCP, port: 3306 }
    - to:                        # 放行 DNS，否则域名全解析不了
        - namespaceSelector: {}
          podSelector:
            matchLabels: { k8s-app: kube-dns }
      ports:
        - { protocol: UDP, port: 53 }
```

**加默认拒绝策略时最容易踩的坑**：忘了放行 DNS 的 53 端口出站，导致所有域名解析失败。

### DNS

| 目标                  | FQDN                                               |
| :-------------------- | :------------------------------------------------- |
| Service（同命名空间） | `web`                                              |
| Service（跨命名空间） | `web.other-ns`                                     |
| Service（完整）       | `web.other-ns.svc.cluster.local`                   |
| StatefulSet Pod       | `mysql-0.mysql-headless.default.svc.cluster.local` |
| Pod（需 Headless）    | `10-244-1-5.default.pod.cluster.local`             |

Pod 内 `/etc/resolv.conf` 的 `search` 域决定了短名称能展开成什么，`ndots:5` 意味着少于 5 个点的域名会先尝试拼接 search 域，这曾是 DNS 查询放大的常见原因。CoreDNS 配置在 `kube-system/coredns` 这个 ConfigMap 里。

```bash
# DNS 排障标准动作
kubectl run tmp --image=busybox:1.28 --rm -it --restart=Never -- nslookup kubernetes.default
kubectl -n kube-system get pod -l k8s-app=kube-dns -o wide
kubectl -n kube-system logs -l k8s-app=kube-dns
```
