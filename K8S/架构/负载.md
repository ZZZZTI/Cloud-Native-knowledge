> 负载控制器：DaemonSet，Job，CronJob，PHA，PDB

------

### 工作负载控制器

```Shell
1. DaemonSet（日志/监控采集器、CNI）
确保集群中每个（或指定标签的）节点上都运行且只运行一个 Pod 副本。
DaemonSet 的副本数由当前集群中匹配条件的 Node 数量自动决定，需设置污点与容忍
专用于日志收集、监控 Agent 和 CNI 网络插件等节点级守护进程。

2. Job（数据迁移、批处理）
执行一次性批处理任务，确保指定数量的 Pod 成功运行到完成（Completed）状态。
需设置 ttlSecondsAfterFinished 自动清理，否则会导致大量已完成的 Pod 堆积。

3. CronJob（定时巡检、报表）
基于 Cron 表达式周期性地创建 Job，执行定时任务。
注意时区默认是 UTC，且需配置 concurrencyPolicy 防止任务并发冲突。

4. HPA (HorizontalPodAutoscaler)（自动扩缩）
根据 CPU/内存或自定义指标，自动弹性调整 Deployment/StatefulSet 的副本数。
强依赖 metrics-server，生产环境必须配置 behavior 缩容冷却时间防抖。
# 期望副本数 = ceil（向上取整）[ 当前副本数 × ( 当前指标值 / 目标指标值 ) ]

5. PDB (PodDisruptionBudget)（节点维护）
保障应用在主动驱逐（排空节点、集群缩容、升级节点内核）时，至少有指定数量的 Pod 保持可用。
只能拦截“自愿中断”操作，无法阻止节点宕机、OOM 等“非自愿中断”。
```

### DaemonSet .yaml

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: my-daemonset
  namespace: default
  labels:
    app.kubernetes.io/name: my-agent
spec:
  # 1. 标签选择器（必须匹配 template.metadata.labels）
  selector:
    matchLabels:
      app: my-agent

  # 2. 更新策略
  updateStrategy:
    type: RollingUpdate       # 默认策略。另一个是 OnDelete（只有手动删除旧 Pod 才会创建新的）
    rollingUpdate:
      maxUnavailable: 1       # 每次更新时，最多允许几个节点上的 Pod 不可用（也可以是百分比 "10%"）
      # maxSurge: 0           # 注意：DaemonSet 的 maxSurge 默认就是 0，且通常不建议设置

  # 3. Pod 模板
  template:
    metadata:
      labels:
        app: my-agent
    spec:
      # --- 系统级关键配置 ---
      # 将 DaemonSet 的优先级设为最高，防止节点资源紧张时被驱逐（kubelet 自身的保护机制）
      priorityClassName: system-node-critical 
      
      # 如果 DaemonSet 需要接管宿主机网络（如 CNI 插件），必须设置以下字段
      hostNetwork: true
      # hostPID: true
      # hostIPC: true
      
      # --- 节点选择与容忍 ---
      # ① 节点选择器：只在带有特定标签的节点上运行（可选）
      nodeSelector:
        kubernetes.io/os: linux
        
      # ② 容忍度（极其重要）：必须容忍节点的污点，否则无法调度到 Master 或特殊节点上
      tolerations:
        # 容忍所有 NoSchedule 的污点（常用于跑遍所有节点，包括 Master）
        - operator: Exists
          effect: NoSchedule
        # 容忍节点未就绪的状态（防止节点刚重启时 Agent 被驱逐，导致节点永远无法恢复）
        - key: node.kubernetes.io/not-ready
          operator: Exists
          effect: NoExecute
          
      # --- 安全上下文 ---
      securityContext:
        # 很多底层 Agent 需要访问宿主机文件系统或网络，需要特权模式
        privileged: true 

      containers:
        - name: agent
          image: my-registry/my-agent:1.0.0
          imagePullPolicy: IfNotPresent
          
          resources:
            requests:
              cpu: 50m
              memory: 64Mi
            limits:
              cpu: 200m
              memory: 256Mi

          # 环境变量注入宿主机的节点信息
          env:
            - name: NODE_NAME
              valueFrom:
              fieldRef:
                fieldPath: spec.nodeName
            - name: POD_IP
              valueFrom:
                fieldRef:
                  fieldPath: status.podIP

          # --- 挂载宿主机目录（DaemonSet 最常见的操作） ---
          volumeMounts:
            - name: varlog
              mountPath: /var/log
              readOnly: true
            - name: docker-sock
              mountPath: /var/run/docker.sock
              readOnly: true
            - name: host-root
              mountPath: /host

      # --- 卷定义 ---
      volumes:
        - name: varlog
          hostPath:
            path: /var/log
            type: Directory
        - name: docker-sock
          hostPath:
            path: /var/run/docker.sock
            type: Socket
        - name: host-root
          hostPath:
            path: /
            type: Directory          
```

### Job / CronJob

```Shell
# ============================================================
# 1. 普通 Job：一次性数据清理任务
# ============================================================
apiVersion: batch/v1
kind: Job
metadata:
  name: one-time-cleanup
  namespace: default
spec:
  # --- 任务执行策略 ---
  # completions: 10                # 总共需要成功完成的 Pod 数量（默认 1）
  # parallelism: 2                 # 允许同时并行运行的 Pod 数量上限（默认 1）
  # --- 失败处理与超时 ---
  backoffLimit: 3                  # 失败最多重试 3 次
  activeDeadlineSeconds: 300       # 整个 Job 的限制时间
  ttlSecondsAfterFinished: 100     # 完成后 100 秒自动清理（防止 Completed Pod 堆积）
  template:
    spec:
      restartPolicy: OnFailure     # 只能是 OnFailure 或 Never
      containers:
        - name: cleanup
          image: busybox:1.36
          command: ["/bin/sh", "-c"]
          args: 
            - |
              echo "开始清理临时文件..."
              sleep 3
              echo "清理完成！"
              exit 0

---
# ============================================================
# 2. CronJob：每天凌晨 2 点执行的数据备份任务
# ============================================================
apiVersion: batch/v1
kind: CronJob
metadata:
  name: daily-backup
  namespace: default
spec:
  schedule: "0 2 * * *"            # Cron 表达式：每天 2:00 执行
  timeZone: "Asia/Shanghai"        # (需 K8s 1.27+) 指定时区，否则默认 UTC
  concurrencyPolicy: Forbid        # 并发策略：上次没跑完，本次直接跳过（防并发冲突）
                                   # Allow（默认）：上次没跑完，下次时间到了继续起新的。
                                   # Replace：杀掉上次没跑完的，起新的。
  startingDeadlineSeconds: 60      # 如果错过了时间点，60 秒内还没起，就放弃本次
  
  # 历史记录保留策略
  successfulJobsHistoryLimit: 3    # 保留 3 个成功的 Job 记录
  failedJobsHistoryLimit: 1        # 保留 1 个失败的 Job 记录供排错
  
  # Job 模板（CronJob 定时创建的就是这里的 Job）
  jobTemplate:
    spec:
      backoffLimit: 2
      ttlSecondsAfterFinished: 600 # Job 跑完后保留 10 分钟让日志被采走，然后清理
      template:
        spec:
          restartPolicy: Never     # 也可以用 OnFailure
          containers:
            - name: backup
              image: busybox:1.36
              command: ["/bin/sh", "-c"]
              args: 
                - |
                  echo "开始备份数据库..."
                  # 假设这里执行 mysqldump 等命令
                  sleep 5
                  echo "备份成功！"
                  exit 0
              resources:
                requests:
                  cpu: 100m
                  memory: 64Mi
                limits:
                  cpu: 200m
                  memory: 128Mi
```

### HPA 

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: my-app-hpa
  namespace: default
spec:
  # 1. 扩缩容目标（必须与目标 Deployment 在同一个 namespace）
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: my-app-deployment

  # 2. 副本数范围
  minReplicas: 2                   # 最小副本数（即使没流量也保留 2 个保证高可用）
  maxReplicas: 10                  # 最大副本数（防止扩缩容导致资源耗尽）

  # 3. 指标配置（可以配多个，HPA 会取计算结果的【最大值】进行扩容）
  metrics:
    # 指标一：基于 CPU 利用率
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70   # 目标：平均 CPU 使用率达到 requests 的 70%

    # 指标二：基于内存利用率（注意：内存通常只扩不缩，因为有 GC 延迟）
    - type: Resource
      resource:
        name: memory
        target:
          type: Utilization
          averageUtilization: 80   # 目标：平均内存使用率达到 requests 的 80%

    # 指标三（示例）：基于自定义业务指标（如 Prometheus 采集的 QPS，需要配合适配器）
    # - type: Pods
    #   pods:
    #     metric:
    #       name: http_requests_per_second
    #     target:
    #       type: AverageValue
    #       averageValue: 1k        # 目标：每个 Pod 每秒处理 1000 个请求

  # 4. 扩缩容行为控制（极其重要，防止指标抖动导致频繁扩缩容）
  behavior:
    # 扩容行为
    scaleUp:
      stabilizationWindowSeconds: 0      # 扩容无需等待，检测到超标立刻扩（默认 0）
      policies:
        - type: Percent
          value: 100                     # 每次扩容最多翻倍（例如从 2 扩到 4，下次从 4 扩到 8）
          periodSeconds: 15              # 每 15 秒允许触发一次扩容
        - type: Pods
          value: 4                       # 或者每次最多加 4 个 Pod
          periodSeconds: 15
      selectPolicy: Max                  # 选择上面策略中允许扩容数量最大的那个
      
    # 缩容行为
    scaleDown:
      stabilizationWindowSeconds: 300    # 【神级防抖】过去 5 分钟内的推荐副本数，取最大值（防止流量闪降立刻缩容）
      policies:
        - type: Percent
          value: 10                      # 每次缩容最多减少当前副本数的 10%
          periodSeconds: 60              # 每 60 秒允许缩容一次（慢慢缩，给应用缓冲时间）
```

### PDB

```Shell
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: my-app-pdb
  namespace: default
spec:
  # 1. 选择要保护的目标 Pod（通常与 Deployment 的标签匹配）
  selector:
    matchLabels:
      app: my-app

  # 2. 中断底线（二选一）
  # 方式 A：保证至少有 2 个 Pod 存活（可以是数字，也可以是百分比 "50%"）
  minAvailable: 2
  
  # 方式 B：最多允许 1 个 Pod 同时不可用
  # maxUnavailable: 1
```
