> 控制器：Deployment，ReplicaSet，StatefulSet，DaemonSet，Job，CronJob

------

### 应用和负载控制器

```Shell
1. Deployment（Web 服务、API）
管理无状态应用，实现滚动更新、版本回滚和故障自愈。
只有修改 spec.template 才会触发发布，底层通过创建新版 RS 来替换旧版 RS。
# Deployment 发布管理（rollout）
kubectl rollout status deployment/<deploy>   # 查看发布进度
kubectl rollout history deployment/<deploy>  # 查看发布历史
kubectl rollout history deployment/<deploy> --revision=3  # 查看指定版本的详情
kubectl rollout undo deployment/<deploy>     # 回滚到上一版本
kubectl rollout undo deployment/<deploy> --to-revision=2  # 回滚到指定版本
kubectl rollout restart deployment/<deploy>  # 滚动重启（不改变镜像，常用于让 Pod 重新拉取配置）
kubectl rollout pause deployment/<deploy>    # 暂停发布
kubectl rollout resume deployment/<deploy>   # 恢复发布
kubectl scale deployment/web --replicas=5    # 扩缩容 Deployment

2. ReplicaSet (RS)（排障时必看）
保证集群中始终有指定数量的 Pod 副本存活。
一般不需要直接创建，它是底层干活的，由 Deployment 统一管理。
# 底层级联关系：Deployment -> RS -> Pod

3. StatefulSet（数据库、消息队列）
管理有状态应用，默认按顺序 0->N 部署和 N->0 缩容，删除 Pod 或控制器时其绑定的 PVC 默认保留。
为每个 Pod 提供固定的网络标识（需 Headless Service）和独立存储。
# 固定的 DNS 记录：<pod-name>.<service-name>.<namespace>.svc.cluster.local
# StatefulSet被删除后，要彻底销毁应用并清空数据，必须手动删 PVC：kubectl delete pvc -l app=my-app

4. DaemonSet（日志/监控采集器、CNI）
确保集群中每个（或指定标签的）节点上都运行且只运行一个 Pod 副本。
DaemonSet 的副本数由当前集群中匹配条件的 Node 数量自动决定，需设置污点与容忍
专用于日志收集、监控 Agent 和 CNI 网络插件等节点级守护进程。

5. Job（数据迁移、批处理）
执行一次性批处理任务，确保指定数量的 Pod 成功运行到完成（Completed）状态。
需设置 ttlSecondsAfterFinished 自动清理，否则会导致大量已完成的 Pod 堆积。

6. CronJob（定时巡检、报表）
基于 Cron 表达式周期性地创建 Job，执行定时任务。
注意时区默认是 UTC，且需配置 concurrencyPolicy 防止任务并发冲突。
```

### Deployment.yaml

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app-deployment
  namespace: default
  labels:
    app.kubernetes.io/name: my-app
    app.kubernetes.io/version: "1.0.0"
  annotations:
    description: "这是一个包含常用语法的 Deployment 模板"
spec:
  # 1. 副本数与版本控制
  replicas: 3
  revisionHistoryLimit: 10        # 保留的历史 RS 数量，用于回滚（默认 10）
  minReadySeconds: 5              # Pod 启动后至少保持 5 秒不崩溃才算“可用”（平滑滚动防抖）
  progressDeadlineSeconds: 600    # 滚动更新超时时间（默认 600 秒），超时则标记为失败

  # 2. 标签选择器（必须匹配 template.metadata.labels）
  selector:
    matchLabels:
      app: my-app
    # matchExpressions:           # 高级选择器（可选）
    #   - {key: env, operator: In, values: [prod]}

  # 3. 更新策略
  strategy:
    type: RollingUpdate           # 默认策略。另一个选项是 Recreate（先杀旧再起新）
    rollingUpdate:
      maxSurge: 25%               # 更新时最多超出期望副本数25%的 Pod（或具体个数）
      maxUnavailable: 25%         # 更新时最多允许25%的 Pod 不可用（Surge与Unavailable不能同时为0）

  # 4. Pod 模板
  template:
    metadata:
      labels:
        app: my-app               # 必须与上面的 selector.matchLabels 匹配
      annotations:
        prometheus.io/scrape: "true" # 监控采集注解
    spec:
      # --- 全局运行与安全 ---
      terminationGracePeriodSeconds: 30  # 优雅停机时间（收到 SIGTERM 后等待时间）
      serviceAccountName: my-app-sa      # 指定运行身份
      securityContext:                   # Pod 级别安全上下文
        runAsNonRoot: true
        runAsUser: 1000
        runAsGroup: 3000
        fsGroup: 2000
      
      # 私有仓库拉取凭证
      imagePullSecrets:
        - name: my-registry-secret

      # --- 节点调度策略 ---
      nodeSelector:
        disktype: ssd
      tolerations:
        - key: "dedicated"
          operator: "Equal"
          value: "web"
          effect: "NoSchedule"
      affinity:
        podAntiAffinity:           # Pod 反亲和：同一应用的副本尽量不在同一节点（高可用）
          preferredDuringSchedulingIgnoredDuringExecution:
            - weight: 100
              podAffinityTerm:
                labelSelector:
                  matchExpressions:
                    - key: app
                      operator: In
                      values: ["my-app"]
                topologyKey: "kubernetes.io/hostname"

      # --- 初始化容器（可选） ---
      initContainers:
        - name: wait-for-db
          image: busybox:1.36
          command: ['sh', '-c', 'until nc -z mysql 3306; do echo waiting; sleep 2; done']

      # --- 主容器 ---
      containers:
        - name: app
          image: my-registry/my-app:1.0.0
          imagePullPolicy: IfNotPresent
          
          # 命令与参数（可选，用于覆盖镜像 ENTRYPOINT/CMD）
          command: ["/bin/sh"]
          args: ["-c", "nginx -g 'daemon off;'"]
          
          ports:
            - name: http
              containerPort: 8080
              protocol: TCP
              
          # 配置注入（环境变量）
          envFrom:
            - configMapRef:
                name: app-config
                optional: false
            - secretRef:
                name: app-secret
                optional: false
          env:
            - name: POD_NAME          # 使用 Downward API 注入 Pod 自身信息
              valueFrom:
                fieldRef:
                  fieldPath: metadata.name
            - name: CUSTOM_VAR
              value: "custom_value"

          # 资源限制
          resources:
            requests:
              cpu: 100m
              memory: 128Mi
            limits:
              cpu: 500m
              memory: 256Mi

          # 存储挂载
          volumeMounts:
            - name: config-vol
              mountPath: /etc/app/config
              readOnly: true
            - name: data-vol
              mountPath: /usr/share/nginx/html

          # 探针配置
          startupProbe:               # 启动探针（防慢启动应用被误杀）
            httpGet:
              path: /healthz
              port: http
            failureThreshold: 30
            periodSeconds: 2
          livenessProbe:              # 存活探针（失败则重启容器）
            httpGet:
              path: /healthz
              port: http
            initialDelaySeconds: 5
            periodSeconds: 10
            timeoutSeconds: 3
            successThreshold: 1
            failureThreshold: 3
          readinessProbe:             # 就绪探针（失败则从 Service Endpoints 中摘除）
            httpGet:
              path: /
              port: http
            initialDelaySeconds: 3
            periodSeconds: 5

          # 容器级安全上下文
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities:
              drop: ["ALL"]
              add: ["NET_BIND_SERVICE"]

          # 生命周期钩子
          lifecycle:
            postStart:
              exec:
                command: ["/bin/sh", "-c", "echo Hello > /tmp/started"]
            preStop:                  # 优雅停机：先摘除流量，等几秒，再让 kubelet 杀进程
              exec:
                command: ["/bin/sh", "-c", "sleep 5"]

      # 卷定义
      volumes:
        - name: config-vol
          configMap:
            name: app-config
            defaultMode: 0644
        - name: data-vol
          persistentVolumeClaim:
            claimName: my-app-pvc
        # 临时目录（配合 readOnlyRootFilesystem: true 使用）
        - name: tmp-vol
          emptyDir: {}
```

### StatefulSet.yaml

```yaml
# ============================================================
# 1. Headless Service (无头服务)
# StatefulSet 必须绑定一个 Headless Service 才能实现稳定的 DNS 解析
# ============================================================
apiVersion: v1
kind: Service
metadata:
  name: my-app-headless
  namespace: default
  labels:
    app: my-app
spec:
  clusterIP: None           # 关键：None 表示无头服务，不分配虚拟 IP
  selector:
    app: my-app             # 必须匹配 StatefulSet 的 Pod 标签
  ports:
    - name: http
      port: 80
      targetPort: 8080
  # publishNotReadyAddresses: true  # 可选：即使 Pod 没就绪也发布 DNS（常用于集群节点互相发现的场景，如 Zookeeper）

---
# ============================================================
# 2. StatefulSet
# ============================================================
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: my-app-sts
  namespace: default
  labels:
    app.kubernetes.io/name: my-app
spec:
  # --- 核心身份标识 ---
  serviceName: my-app-headless   # 必须指定上面的 Headless Service 名称
  replicas: 3                    # 副本数

  # --- 管理策略 ---
  # OrderedReady (默认)：按 0 -> 1 -> 2 顺序启动，缩容按 2 -> 1 -> 0 倒序
  # Parallel：所有 Pod 同时并行启动和停止（适用于不需要启动依赖的应用）
  podManagementPolicy: OrderedReady
  
  # 保留历史版本数（用于回滚，默认 10）
  revisionHistoryLimit: 10

  # --- 更新策略 ---
  updateStrategy:
    type: RollingUpdate
    rollingUpdate:
      # 默认 0，表示全量更新。
      # 如果设为 1，则只会更新序号 >= 1 的 Pod（0 号 Pod 保持不变），常用于金丝雀发布或主从架构（先升从，最后升主）。
      partition: 0 

  # --- 标签选择器 ---
  selector:
    matchLabels:
      app: my-app

  # --- Pod 模板 (与 Deployment 基本一致) ---
  template:
    metadata:
      labels:
        app: my-app
      annotations:
        prometheus.io/scrape: "true"
    spec:
      terminationGracePeriodSeconds: 30   # 优雅停机时间（对数据库尤其重要，需留足刷盘时间）
      securityContext:
        runAsNonRoot: true
        runAsUser: 1000
        fsGroup: 2000                     # 【重要】影响挂载的 PVC 目录权限，确保容器内有写权限
      
      # 调度与亲和性
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution: # 强制要求每个 Pod 不在同一个节点（高可用）
            - labelSelector:
                matchExpressions:
                  - key: app
                    operator: In
                    values: ["my-app"]
              topologyKey: "kubernetes.io/hostname"

      containers:
        - name: app
          image: my-registry/my-db:1.0.0
          imagePullPolicy: IfNotPresent
          
          ports:
            - name: http
              containerPort: 8080
            # 很多有状态应用（如 K8s 体系下的 etcd）需要 Peer 端口
            - name: peer
              containerPort: 2380

          env:
            # 【经典操作】通过 Downward API 将 Pod 的序号（如 0,1,2）注入给应用
            # 应用通过读取这个变量，就能知道自己当前是主节点还是从节点
            - name: POD_NAME
              valueFrom:
                fieldRef:
                  fieldPath: metadata.name
            
          resources:
            requests:
              cpu: 500m
              memory: 1Gi
            limits:
              cpu: 1000m
              memory: 2Gi

          # 探针配置
          readinessProbe:
            tcpSocket:
              port: 8080
            initialDelaySeconds: 10
            periodSeconds: 5
          livenessProbe:
            httpGet:
              path: /healthz
              port: 8080
            initialDelaySeconds: 30
            periodSeconds: 10

          # 存储挂载：引用下方 volumeClaimTemplates 生成的 PVC
          volumeMounts:
            - name: data            # 必须匹配 volumeClaimTemplates 中的 name
              mountPath: /var/lib/app/data
            
            # 如果有多个存储需求，可以继续加（如挂载日志或配置）
            - name: config-vol
              mountPath: /etc/app/config
              readOnly: true
              
          # 初始化容器（常用于修改数据目录权限，因为 fsGroup 在某些 NFS 下不生效）
          # initContainers:
          #   - name: init-permissions
          #     image: busybox
          #     command: ["sh", "-c", "chown -R 1000:2000 /var/lib/app/data"]
          #     volumeMounts:
          #       - name: data
          #         mountPath: /var/lib/app/data

      # 常规的临时卷定义（PVC 不在这里定义，而在下面）
      volumes:
        - name: config-vol
          configMap:
            name: app-config

  # ============================================================
  # 3. volumeClaimTemplates (PVC 模板)
  # 这是 StatefulSet 最大的特色：自动为每个 Pod 创建独立的 PVC
  # 命名规则：<模板name>-<sts名称>-<序号> => 比如 data-my-app-sts-0
  # ============================================================
  volumeClaimTemplates:
    - metadata:
        name: data                # 名字必须与上面 volumeMounts 里的 name 一致
      spec:
        accessModes: [ "ReadWriteOnce" ]   # 有状态应用大多是块存储，使用 RWO
        storageClassName: "standard"       # 指定存储类
        resources:
          requests:
            storage: 10Gi
```

### DaemonSet .yaml

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: my-daemonset
  namespace: default
  labels:
    app.kubernetes.io/name: my-agent
spec:
  # 1. 标签选择器（必须匹配 template.metadata.labels）
  selector:
    matchLabels:
      app: my-agent

  # 2. 更新策略
  updateStrategy:
    type: RollingUpdate       # 默认策略。另一个是 OnDelete（只有手动删除旧 Pod 才会创建新的）
    rollingUpdate:
      maxUnavailable: 1       # 每次更新时，最多允许几个节点上的 Pod 不可用（也可以是百分比 "10%"）
      # maxSurge: 0           # 注意：DaemonSet 的 maxSurge 默认就是 0，且通常不建议设置

  # 3. Pod 模板
  template:
    metadata:
      labels:
        app: my-agent
    spec:
      # --- 系统级关键配置 ---
      # 将 DaemonSet 的优先级设为最高，防止节点资源紧张时被驱逐（kubelet 自身的保护机制）
      priorityClassName: system-node-critical 
      
      # 如果 DaemonSet 需要接管宿主机网络（如 CNI 插件），必须设置以下字段
      hostNetwork: true
      # hostPID: true
      # hostIPC: true
      
      # --- 节点选择与容忍 ---
      # ① 节点选择器：只在带有特定标签的节点上运行（可选）
      nodeSelector:
        kubernetes.io/os: linux
        
      # ② 容忍度（极其重要）：必须容忍节点的污点，否则无法调度到 Master 或特殊节点上
      tolerations:
        # 容忍所有 NoSchedule 的污点（常用于跑遍所有节点，包括 Master）
        - operator: Exists
          effect: NoSchedule
        # 容忍节点未就绪的状态（防止节点刚重启时 Agent 被驱逐，导致节点永远无法恢复）
        - key: node.kubernetes.io/not-ready
          operator: Exists
          effect: NoExecute
          
      # --- 安全上下文 ---
      securityContext:
        # 很多底层 Agent 需要访问宿主机文件系统或网络，需要特权模式
        privileged: true 

      containers:
        - name: agent
          image: my-registry/my-agent:1.0.0
          imagePullPolicy: IfNotPresent
          
          resources:
            requests:
              cpu: 50m
              memory: 64Mi
            limits:
              cpu: 200m
              memory: 256Mi

          # 环境变量注入宿主机的节点信息
          env:
            - name: NODE_NAME
              valueFrom:
              fieldRef:
                fieldPath: spec.nodeName
            - name: POD_IP
              valueFrom:
                fieldRef:
                  fieldPath: status.podIP

          # --- 挂载宿主机目录（DaemonSet 最常见的操作） ---
          volumeMounts:
            - name: varlog
              mountPath: /var/log
              readOnly: true
            - name: docker-sock
              mountPath: /var/run/docker.sock
              readOnly: true
            - name: host-root
              mountPath: /host

      # --- 卷定义 ---
      volumes:
        - name: varlog
          hostPath:
            path: /var/log
            type: Directory
        - name: docker-sock
          hostPath:
            path: /var/run/docker.sock
            type: Socket
        - name: host-root
          hostPath:
            path: /
            type: Directory          
```

### Job / CronJob

```yaml
# ============================================================
# 1. 普通 Job：一次性数据清理任务
# ============================================================
apiVersion: batch/v1
kind: Job
metadata:
  name: one-time-cleanup
  namespace: default
spec:
  # --- 任务执行策略 ---
  # completions: 10                # 总共需要成功完成的 Pod 数量（默认 1）
  # parallelism: 2                 # 允许同时并行运行的 Pod 数量上限（默认 1）
  # --- 失败处理与超时 ---
  backoffLimit: 3                  # 失败最多重试 3 次
  activeDeadlineSeconds: 300       # 整个 Job 的限制时间
  ttlSecondsAfterFinished: 100     # 完成后 100 秒自动清理（防止 Completed Pod 堆积）
  template:
    spec:
      restartPolicy: OnFailure     # 只能是 OnFailure 或 Never
      containers:
        - name: cleanup
          image: busybox:1.36
          command: ["/bin/sh", "-c"]
          args: 
            - |
              echo "开始清理临时文件..."
              sleep 3
              echo "清理完成！"
              exit 0

---
# ============================================================
# 2. CronJob：每天凌晨 2 点执行的数据备份任务
# ============================================================
apiVersion: batch/v1
kind: CronJob
metadata:
  name: daily-backup
  namespace: default
spec:
  schedule: "0 2 * * *"            # Cron 表达式：每天 2:00 执行
  timeZone: "Asia/Shanghai"        # (需 K8s 1.27+) 指定时区，否则默认 UTC
  concurrencyPolicy: Forbid        # 并发策略：上次没跑完，本次直接跳过（防并发冲突）
                                   # Allow（默认）：上次没跑完，下次时间到了继续起新的。
                                   # Replace：杀掉上次没跑完的，起新的。
  startingDeadlineSeconds: 60      # 如果错过了时间点，60 秒内还没起，就放弃本次
  
  # 历史记录保留策略
  successfulJobsHistoryLimit: 3    # 保留 3 个成功的 Job 记录
  failedJobsHistoryLimit: 1        # 保留 1 个失败的 Job 记录供排错
  
  # Job 模板（CronJob 定时创建的就是这里的 Job）
  jobTemplate:
    spec:
      backoffLimit: 2
      ttlSecondsAfterFinished: 600 # Job 跑完后保留 10 分钟让日志被采走，然后清理
      template:
        spec:
          restartPolicy: Never     # 也可以用 OnFailure
          containers:
            - name: backup
              image: busybox:1.36
              command: ["/bin/sh", "-c"]
              args: 
                - |
                  echo "开始备份数据库..."
                  # 假设这里执行 mysqldump 等命令
                  sleep 5
                  echo "备份成功！"
                  exit 0
              resources:
                requests:
                  cpu: 100m
                  memory: 64Mi
                limits:
                  cpu: 200m
                  memory: 128Mi
```
