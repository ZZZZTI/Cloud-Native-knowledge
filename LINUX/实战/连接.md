> 网络与连接
> 覆盖：SSH、网络不通、DNS、TIME_WAIT、CLOSE_WAIT、SYN_RECV、防火墙、conntrack。

## 场景 1：SSH 登录很慢

**现象**：`ssh user@host` 输入密码后要等 10～30 秒才进入 Shell，登录后操作正常。

**可能原因**：

- `UseDNS yes` 反向解析慢
- GSSAPI 认证超时
- PAM/SSSD/LDAP 慢
- 家目录在 NFS/autofs 上
- Shell 启动脚本里有耗时命令

**排查命令**：

```bash
ssh -vvv user@host  # 调试 SSH 连接
time ssh user@host true  # 统计 SSH 登录耗时
sshd -T | grep -Ei 'usedns|gssapi|pubkey|password'  # 查看 sshd 生效配置
grep -Ei 'usedns|gssapi' /etc/ssh/sshd_config  # 检查 sshd 配置文件
journalctl -u sshd -n 100 --no-pager  # 查看服务日志
tail -n 100 /var/log/secure  # 查看文件尾部
dig -x <客户端IP>  # 反向 DNS 解析
getent hosts <客户端IP>  # 查询系统解析结果
```

**处理命令**：

```bash
# /etc/ssh/sshd_config
# 关闭 SSH 反向 DNS
UseDNS no
# 关闭 GSSAPI 认证
GSSAPIAuthentication no

sshd -t  # 测试 sshd 配置
systemctl reload sshd  # 平滑重载服务
```

**注意**：如果认证完成后才慢，重点查 PAM、SSSD、家目录挂载和 `.bashrc`。

## 场景 2：SSH 公钥登录失败

**现象**：配置了免密登录，但仍然提示输入密码，或直接 `Permission denied (publickey)`。

**可能原因**：

- 私钥/公钥不匹配
- `authorized_keys` 权限或属主不对
- 家目录权限过宽
- SELinux 上下文错误
- sshd 禁止 PubkeyAuthentication
- 登录用户被 AllowUsers/DenyUsers 限制

**排查命令**：

```bash
ssh -vvv user@host  # 调试 SSH 连接
ls -ld ~ ~/.ssh  # 查看目录/文件权限
ls -l ~/.ssh/authorized_keys  # 查看文件权限
namei -l ~/.ssh/authorized_keys  # 检查路径权限
sshd -T | grep -Ei 'pubkey|authorizedkeys|permitrootlogin|allowusers'  # 查看 sshd 生效配置
tail -n 100 /var/log/secure  # 查看文件尾部
ausearch -m avc -ts recent  # 查询审计日志
```

**处理命令**：

```bash
chmod 700 ~/.ssh  # 设置 SSH 目录权限
chmod 600 ~/.ssh/authorized_keys  # 设置公钥权限
chown -R user:user ~/.ssh  # 修改文件属主
restorecon -Rv ~/.ssh  # 恢复 SELinux 上下文

# 测试
ssh -i ~/.ssh/id_ed25519 user@host  # 指定私钥登录
```

**注意**：私钥权限必须是 `600`，家目录不能 group/other 可写；SELinux 下还要看 `~/.ssh` 的上下文。

## 场景 3：网络不通或丢包

**现象**：从本机访问目标 IP 或端口超时，其他机器访问正常，或 `ping` 有丢包。

**可能原因**：

- 网卡 down、IP/掩码/网关错误
- 路由缺失或走错网卡
- ARP 异常
- 防火墙/安全组丢包
- 链路质量、MTU、上游网络问题

**排查命令**：

```bash
ip addr  # 查看 IP 地址
ip link  # 查看网卡
ip route  # 查看路由
ip route get <目标IP>  # 查看选路结果
ip neigh  # 查看 ARP 表
ping -c 3 <网关>  # 测试连通性
ping -c 3 <目标IP>  # 测试连通性
ping -c 3 8.8.8.8  # 测试连通性
nc -vz <目标IP> <端口>  # 测试端口连通性
traceroute -n <目标IP>  # 跟踪路由
mtr -rw <目标IP>  # 路由与丢包诊断
tcpdump -i any -nn host <目标IP> and port <端口>  # 抓包分析
ethtool eth0  # 查看网卡状态
```

MTU 排查：

```bash
ping -M do -s 1472 -c 3 <目标IP>  # 测试 MTU
```

**处理命令**：

```bash
ip link set eth0 up  # 启用网卡
ip route add <网段> via <网关> dev eth0  # 添加路由
systemctl restart NetworkManager  # 重启服务
# 防火墙放行对应端口
firewall-cmd --permanent --add-port=<端口>/tcp  # 管理 firewalld 规则
firewall-cmd --reload  # 管理 firewalld 规则
```

**注意**：先分层：本机地址/路由 → 链路 → 端口监听 → 中间设备 → 抓包。只有 SYN 没有 SYN-ACK，通常是防火墙或服务未监听。

## 场景 4：DNS 解析失败

**现象**：`ping www.example.com` 报 `Unknown host`，但 `ping 8.8.8.8` 正常。

**可能原因**：

- `/etc/resolv.conf` 配置错误
- DNS 服务器不可达或被防火墙拦截
- `nsswitch.conf` 顺序不对
- `/etc/hosts` 被改错
- systemd-resolved/NetworkManager 覆盖配置

**排查命令**：

```bash
cat /etc/resolv.conf  # 查看 DNS 配置
cat /etc/nsswitch.conf  # 查看名称服务顺序
cat /etc/hosts  # 查看 hosts 解析
getent hosts www.example.com  # 查询系统解析结果
dig www.example.com  # DNS 查询
dig @8.8.8.8 www.example.com  # 指定 DNS 服务器查询
dig +trace www.example.com  # 跟踪 DNS 解析
resolvectl status  # 查看 DNS 解析状态
```

**处理命令**：

```bash
# 临时指定 DNS
echo 'nameserver 8.8.8.8' > /etc/resolv.conf  # 临时修改 DNS

# NetworkManager 环境
nmcli connection modify <连接名> ipv4.dns "8.8.8.8 114.114.114.114"  # 管理 NetworkManager
nmcli connection up <连接名>  # 管理 NetworkManager

# systemd-resolved
systemctl restart systemd-resolved  # 重启服务
```

**注意**：`ping` 和 `curl` 可能使用不同解析路径，排查时用 `getent hosts` 验证系统解析结果。

## 场景 5：TIME_WAIT 过多

**现象**：`ss -s` 显示 `TIME_WAIT` 数量很大，担心端口耗尽。

**可能原因**：

- 大量短连接，主动关闭方是本机
- 没有连接池/keep-alive
- QPS 高、请求时间短
- 客户端端口范围不足

**排查命令**：

```bash
ss -s  # 查看连接状态汇总
ss -tan state time-wait | wc -l  # 统计 TIME_WAIT
ss -tan state time-wait | head  # 统计 TIME_WAIT
ss -tan state time-wait | awk 'NR>1 {print $5}' | sed 's/:[0-9]*$//' | sort | uniq -c | sort -nr | head  # 统计 TIME_WAIT
```

**处理命令**：

```bash
# 应用侧：连接池、keep-alive、减少短连接
# 系统侧：
sysctl -w net.ipv4.tcp_tw_reuse=1  # 临时修改内核参数
sysctl -w net.ipv4.tcp_fin_timeout=15  # 临时修改内核参数
sysctl -w net.ipv4.ip_local_port_range="10000 65000"  # 临时修改内核参数
```

**注意**：`TIME_WAIT` 是正常状态，不是 bug；不要使用已移除的 `tcp_tw_recycle`。根治靠减少短连接。

## 场景 6：CLOSE_WAIT 过多

**现象**：`ss -tan state close-wait` 数量持续增长，最终连接数耗尽。

**可能原因**：

- 应用收到 FIN 后没有调用 `close()`
- 连接泄漏、线程阻塞、异常分支未释放
- 连接池只借不还
- 代码 bug

**排查命令**：

```bash
ss -tan state close-wait | wc -l  # 统计 CLOSE_WAIT
ss -tanp state close-wait | head  # 查看 CLOSE_WAIT 连接
lsof -i :<端口>  # 查看端口占用
jstack <PID> > /tmp/jstack.txt  # 导出 Java 线程栈
grep -nE 'socketRead0|socketWrite0|epollWait|WAITING|BLOCKED' /tmp/jstack.txt | head -50  # 查找线程栈关键字
```

**处理命令**：

```bash
# 临时止血：重启服务
systemctl restart <service>  # 重启服务

# 根治：修复应用关闭连接逻辑、连接池泄漏
```

**注意**：`CLOSE_WAIT` 是应用问题，调内核参数没用；不要把它和 `TIME_WAIT` 混为一谈。

## 场景 7：SYN_RECV 大量堆积

**现象**：`ss -s` 显示 `SYN-RECV` 数量很大，新连接变慢或失败，`netstat -s` 出现 listen overflow。

**可能原因**：

- SYN flood 或恶意扫描
- `somaxconn`、`tcp_max_syn_backlog` 太小
- 应用 accept 太慢，已完成握手队列堆积
- 防火墙/负载均衡转发异常

**排查命令**：

```bash
ss -s  # 查看连接状态汇总
ss -tan state syn-recv | wc -l  # 统计 SYN_RECV
ss -lnt  # 查看监听队列
netstat -s | grep -iE 'syn|listen|overflow'  # 查看 SYN/队列异常
nstat -az | grep -iE 'SynRetrans|ListenOverflows|ListenDrops'  # 查看网络统计
sysctl net.core.somaxconn  # 查看 accept 队列上限
sysctl net.ipv4.tcp_max_syn_backlog  # 查看 SYN 队列上限
```

**处理命令**：

```bash
sysctl -w net.core.somaxconn=65535  # 提高 accept 队列
sysctl -w net.ipv4.tcp_max_syn_backlog=65535  # 提高 SYN 队列
sysctl -w net.ipv4.tcp_syncookies=1  # 开启 SYN Cookie
# 应用侧调大 listen backlog，例如 Nginx 的 listen backlog=8192
# 确认是攻击后，在防火墙/清洗设备上限速或封禁
```

**注意**：`sysctl -w` 只是临时生效，持久化写入 `/etc/sysctl.d/`；不要只调参数不查应用 accept 和攻击流量。

## 场景 8：防火墙误封 SSH

**现象**：修改 iptables/firewalld 后 SSH 断开，重新连接超时；控制台还能登录。

**可能原因**：

- 默认策略改成 DROP，没放行 22
- 没有放行 `ESTABLISHED,RELATED`
- 改了 SSH 端口但防火墙没同步
- fail2ban 把管理 IP 封了

**排查命令**：

```bash
iptables -L -n -v --line-numbers  # 查看 filter 表规则
iptables -t nat -L -n -v  # 查看 nat 表规则
firewall-cmd --list-all  # 查看 firewalld 规则
fail2ban-client status sshd  # 查看 SSH 封禁列表
ss -lntp | grep ':22'  # 确认 SSH 监听端口
```

**处理命令**：

```bash
# 通过控制台/带外管理进入，先放行 SSH
iptables -I INPUT 1 -p tcp --dport 22 -j ACCEPT  # 放行 SSH
iptables -I INPUT 2 -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT  # 放行已建立连接

firewall-cmd --permanent --add-service=ssh  # firewalld 放行 SSH
firewall-cmd --reload  # 重载 firewalld

fail2ban-client set sshd unbanip <IP>  # 解封管理 IP
```

**注意**：远程改防火墙前，先 `iptables-save` 备份，并留一个“定时回滚”或控制台通道；不要把 SSH 规则放在 DROP 之后。

## 场景 9：conntrack 表满 / 端口耗尽

**现象**：日志出现 `nf_conntrack: table full, dropping packet`，新连接失败，`ss` 中 TIME_WAIT 很多。

**可能原因**：

- `nf_conntrack_max` 太小
- NAT/防火墙场景连接数过多
- 短连接太多、没有连接池
- 本地端口范围不够

**排查命令**：

```bash
dmesg -T | grep -i conntrack  # 查看 conntrack 报错
sysctl net.netfilter.nf_conntrack_count  # 查看当前 conntrack 数量
sysctl net.netfilter.nf_conntrack_max  # 查看 conntrack 上限
cat /proc/sys/net/netfilter/nf_conntrack_count  # 查看当前连接跟踪数
ss -s  # 查看连接状态汇总
ss -tan state time-wait | wc -l  # 统计 TIME_WAIT
sysctl net.ipv4.ip_local_port_range  # 查看本地端口范围
lsmod | grep nf_conntrack  # 查看 conntrack 模块
```

**处理命令**：

```bash
sysctl -w net.netfilter.nf_conntrack_max=1048576  # 提高 conntrack 上限
sysctl -w net.netfilter.nf_conntrack_tcp_timeout_established=600  # 缩短 Established 超时
sysctl -w net.ipv4.ip_local_port_range="10000 65000"  # 扩大本地端口范围
# 应用侧使用连接池、keep-alive，减少短连接
```

**注意**：conntrack 上限越高占用内存越多；不要只调参数，要查 NAT/防火墙规则和短连接来源。

> 备注：命令以 Linux（GNU 工具链）为准；生产环境执行删除、重启、`kill -9`、`fsck`、改权限前，先确认影响范围。
